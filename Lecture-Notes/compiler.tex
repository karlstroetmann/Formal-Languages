\noindent
In this chapter, we construct a compiler that translates a fragment of the \mytt{C} language into \textsl{Java}
assembler. The fragment of the \mytt{C} language translated by the compiler is referred to as
\blue{\textsl{Integer}-\mytt{C}}, \index{Integer-C@\textsl{Integer}-\mytt{C}} because only the data type \mytt{int} is
available. Although it would be feasible to support additional data types, the extra effort would no longer be
proportionate to the educational benefit of the example. 

A compiler essentially consists of the following components:
\begin{enumerate}
\item The scanner reads the file to be translated and breaks it down into a sequence of tokens.
\item The parser reads the sequence of tokens and produces an abstract syntax tree as a result.

      We will generate both the scanner and the parser with \simtextsc{Larkita} from a single grammar.
\item The type-checker checks the abstract syntax tree for type errors. Since the language
      \textsl{Integer}-\mytt{C} contains only a single data type, this phase is not needed for our compiler. 
\item The code generator then translates the parse tree into a sequence of assembler commands that conform to
      the syntax of \textsl{Jasmin}. 
\item This can be followed by an \emph{optimization phase}.   Due to time constraints we cannot cover this
      topic. 
\item The resulting assembler program can be translated into Java bytecode using \textsl{Jasmin}.
\item The Java bytecode is then executed by the \simtextsc{Jvm}, i.e.~the \textsl{Java} virtual machine.
\end{enumerate}
In compilers whose target code is a \simtextsc{Risc} assembler program, a code similar to \simtextsc{Jvm} code is
usually generated first. Such a code is referred to as \emph{intermediate code}. It then remains the task of a
so-called \emph{backend} to generate an assembler program for a given processor architecture. The most
challenging task here is to find a register allocation for the variables, such that as many variables as
possible can be held in registers.

\noindent
We now introduce the language \textsl{Integer}-\texttt{C}, which our compiler is intended to translate. In this
context, we also refer to it as the \emph{source language} of our compiler. Figure \ref{fig:compiler.ebnf} on
page \pageref{fig:compiler.ebnf} shows the grammar of the source language in Extended Backus-Naur Form
(\simtextsc{Ebnf}). The grammar for \textsl{Integer}-\texttt{C} uses the following terminals: 
\begin{enumerate}
\item \simtextsc{Id} is an abbreviation for \blue{Identifier} and represents a sequence of digits, letters, and underscores that begins with a letter. An \simtextsc{Id} designates either a variable or the name of a function.
\item \simtextsc{Number} stands for a sequence of digits interpreted as a decimal number.
\item In addition, there are a number of operators such as \texttt{"+"}, \texttt{"-"}, etc., as well as keywords like \texttt{"if"}, \texttt{"else"}, and \texttt{"while"}.
\end{enumerate}
According to the grammar provided above, a program is a list of functions. A function consists of the
declaration of its signature, followed by a list of declarations (\textsl{decl}) and commands (\textsl{stmt})
enclosed in curly braces.  The grammar shown
in Figure \ref{fig:compiler.ebnf} is ambiguous:
\pagebreak

\begin{enumerate}
\item The grammar has the \blue{Dangling-Else Problem}\index{dangling else problem}.  We will see that the
      LR(1) parser generated by \simtextsc{Larkita} resolves this problem in the way we want.
\item The rules for arithmetic and Boolean expressions do not specify the precedences and associativities of
      the operators.  We will encode this information into the grammar by \blue{stratifying} it, i.e.~by
      introducing one syntactical variable for every precedence level.
\end{enumerate}

\section{Developing the  Scanner and the Parser}
We construct both the scanner and the parser using \simtextsc{Larkita}.  In contrast to parser generators like
\simtextsc{Ply}, which separate the specification of the scanner from the specification of the parser,
\simtextsc{Larkita} reads a \emph{single} grammar that specifies both the tokens and the grammar rules.  Recall that
the names of terminals are written in upper case, while the names of syntactical variables are written in
lower case.  We build this grammar as a string: The part of the grammar that describes the scanner is collected in
the variable \mytt{terminal\_definitions}, while the grammar rules are collected in the variable \mytt{syntax}.
At the end, both strings are concatenated.  The notebook
\\[0.2cm]
\hspace*{1.3cm}
\href{https://github.com/karlstroetmann/Formal-Languages/blob/master/Python/Chapter-13/Compiler.ipynb}{\texttt{Python/Chapter-13/Compiler.ipynb}}
\\[0.2cm]
contains the complete compiler.  In this notebook, the strings \mytt{terminal\_definitions} and \mytt{syntax}
are built step by step.  For the presentation in these lecture notes, we have combined these steps.

\noindent
Figure \ref{fig:Compiler.ipynb:lex} on page \pageref{fig:Compiler.ipynb:lex} shows the specification of the
scanner.
\begin{enumerate}
\item Line 4 defines the token \mytt{NUMBER}, which specifies a natural number.  In \simtextsc{Larkita}, a regular
      expression is enclosed in forward slashes.
\item Line 6--11 define the tokens for those operators that consist of more than one character.  Strictly
      speaking, these definitions are not necessary: A string that occurs literally inside a grammar rule, for
      example \quoted{==}, is automatically turned into an \blue{anonymous terminal}.  However, the name that
      \simtextsc{Larkita} generates for an anonymous terminal built from a symbol like \quoted{==} has the form
      \mytt{\_\_ANON\_1}, and such a name is of little help when we inspect the token stream.  If a terminal with
      the same definition has been declared explicitly, \simtextsc{Larkita} uses this terminal instead of creating
      an anonymous one.  Hence, these declarations only serve to give the tokens readable names.  Note that a
      terminal that is defined by a string needs no escaping: We can simply write \quoted{||}.  Furthermore,
      \simtextsc{Larkita} prefers longer strings, so \quoted{!=} is preferred over \quoted{!} and \quoted{<=} is
      preferred over \quoted{<}.

      The operators that consist of a single character need no declaration at all:  \simtextsc{Larkita} gives
      the corresponding anonymous terminals names like \mytt{PLUS}, \mytt{LPAR}, or \mytt{SEMICOLON}.
\item Our version of \texttt{C} supports both single-line comments and multi-line comments.  These are
      defined by the token \mytt{COMMENT} in line 13 and 14, which shows that a terminal can be defined as an
      alternative of several regular expressions.
      \begin{enumerate}[(a)]
      \item Multi-line comments start with the string \quoted{/*} and end with the string \quoted{*/}.
            Note that we have to use the \emph{non-greedy} quantifier \quoted{*?}.  Otherwise, a line like
            \\[0.2cm]
            \hspace*{1.3cm}
            \mytt{/* blah */ a = 1; /* blub */}
            \\[0.2cm]
            would be recognized as a single comment.
      \item Single-line comments start with the string \quoted{//} and extend to the end of the line.
      \end{enumerate}
      As the forward slash is the delimiter of a regular expression in \simtextsc{Larkita}, every occurrence of
      the character \quoted{/} inside a regular expression has to be escaped as \quoted{\symbol{92}/}.
      The directive \mytt{\%ignore} in line 15 tells the scanner to discard all comments, so that they never
      show up in the token stream.
\item The most interesting aspect is the implementation of keywords like \quoted{while} or \quoted{return}.
      Syntactically, all keywords are identifiers, i.e.~they are also matched by the regular expression defining
      the token \mytt{NAME} in line 17.  In the grammar of Figure \ref{fig:compiler.ebnf}, this token has been
      called \simtextsc{Id}.  \simtextsc{Larkita} deals with keywords automatically:  If a string terminal
      like \quoted{if} is also matched by the regular expression of another terminal, then \simtextsc{Larkita}
      first scans a \mytt{NAME} and afterwards checks whether the resulting string is one of the keywords.  If
      it is, the \blue{token type}\index{token type} is changed accordingly.  Because of this, the string
      \mytt{iffy} is scanned as a single \mytt{NAME} and not as the keyword \mytt{if} followed by the
      identifier \mytt{fy}.  Therefore, the keywords do not need to be declared as tokens.  They are simply
      written as strings inside the grammar rules.
\item Finally, line 19 specifies that white space is ignored.  \simtextsc{Larkita} keeps track of line numbers
      and column numbers on its own:  every token $t$ provides the attributes \mytt{t.line} and \mytt{t.column},
      which are used in error messages.
\end{enumerate}

    """

Now we are ready to present the grammar rules.  As \simtextsc{Larkita} supports \simtextsc{Ebnf}, the grammar
shown in Figure \ref{fig:compiler.ebnf} can be used nearly unchanged.  There are only two things we have to take
care of: First, the rules for arithmetic and Boolean expressions have to be stratified.  Second, the grammar
determines the abstract syntax tree that the parser returns:  The string literals of an alternative form the
\blue{head} of the tuple that is built for this alternative, while all other symbols become its children.  We
choose the aliases and the literals that are ignored in such a way that the parser returns exactly the nested
tuples that are processed by our code generator.
Figure \ref{fig:Compiler.ipynb-1} on page \pageref{fig:Compiler.ipynb-1} shows the first part of the grammar.
\begin{enumerate}
\item Line 2 specifies that a \mytt{program} is a non-empty list of function definitions.  The alias
      \quoted{.} replaces the head of the tuple, so a program consisting of the functions $f_1$, $\cdots$, $f_n$
      is represented as the tuple $(\squoted{.}, f_1, \cdots, f_n)$.
\item A \mytt{function} definition starts with the keyword \quoted{int} that is followed by the name of the
      function, an opening parenthesis, a list of the parameters of the function, a closing parenthesis,
      an opening brace, a list of declarations, a list of statements, and finally a closing brace.
      The strings \quoted{int}, \quoted{(}, \quoted{)}, \quoted{\{}, and \quoted{\}} are literals.  They would
      only contribute to the head of the tuple, but the alias \quoted{fct} replaces this head.  Therefore, a
      function definition is represented as a tuple with five components:  the string \squoted{fct}, the name of
      the function, its parameters, its declarations, and its statements.

      The initial version of the programming language \texttt{C}, as detailed in the book
      ``\emph{The C Programming Language}'' \cite{kernighan:1978}, required that all variable declarations
      precede any statements, prohibiting the mixing of declarations and statements. While this limitation was
      lifted in subsequent versions of the language, our implementation still enforces this restriction.
\item The directive in line 6 removes the parentheses, the braces, and the semicolon from the heads of
      \emph{all} alternatives of the grammar, since these literals carry no information.
\item The syntactical variables \mytt{parameters}, \mytt{declarations}, and \mytt{statements} defined in line
      8, 10, and 12 describe lists.  Using the \simtextsc{Ebnf} operators \quoted{*} and \quoted{?}, one rule per
      list suffices.  Note that a parameter list may be empty and that different parameters are separated by
      commas, while every declaration is terminated by a semicolon.  The children of a repetition are spliced
      into the tuple of the alternative, and the alias \quoted{.} replaces the head.  Hence, every list is
      represented as a tuple of the form $(\squoted{.}, \textsl{item}_1, \cdots, \textsl{item}_n)$.  The tuples
      of \mytt{parameters} and \mytt{declarations} contain only the tokens of type \mytt{NAME}, since all other
      symbols occurring in these rules are literals.
\item Line 14--20 define the syntactical variable \mytt{statement}.  As the parentheses and the semicolon are
      ignored, the heads of the tuples are the keywords \squoted{if}, \squoted{while}, and \squoted{return} and
      the operator \squoted{=}.  The alternative in line 17 gets the alias \quoted{if-else}, since otherwise its
      head would be the tuple \mytt{('if', 'else')}.  As the braces and the semicolon are ignored, a block and an
      expression statement consist of a single symbol.  Therefore, a block is represented by the list of its
      statements, while an expression statement is represented by the expression itself.

      The two alternatives in line 16 and line 17 cause the \blue{dangling else}
      problem:  When the parser has read a statement of the form
      \\[0.2cm]
      \hspace*{1.3cm}
      \mytt{if (} \textsl{bool\_expr} \mytt{)} \textsl{statement}
      \\[0.2cm]
      and the next token is the keyword \quoted{else}, then the parser can either \emph{reduce} this statement or
      it can \emph{shift} the token \quoted{else}.  \simtextsc{Larkita} resolves a shift-reduce conflict in favour of
      shifting.  This is exactly what we want:  the keyword \quoted{else} is attached to the innermost
      \quoted{if} that does not yet have an \quoted{else} part.  Hence, a statement of the form
      \\[0.2cm]
      \hspace*{1.3cm}
      \mytt{if (a == 1) if (b == 1) x = 2; else x = 3;}
      \\[0.2cm]
      is interpreted as
      \\[0.2cm]
      \hspace*{1.3cm}
      \mytt{if (a == 1) \{ if (b == 1) x = 2; else x = 3; \}}.
\end{enumerate}

    syntax = syntax + r"""
    bool_expr: bool_expr "||" conjunction
             | conjunction

    conjunction: conjunction "&&" negation

        | product

    product: product ("*" | "/" | "%") factor

          | NAME
          | NAME "(" [expr ("," expr)*] ")"   -> "call"
          | "(" expr ")"
    """

\noindent
Figure \ref{fig:Compiler.ipynb-2} on page \pageref{fig:Compiler.ipynb-2} shows the grammar rules for Boolean and
arithmetic expressions.  \simtextsc{Larkita} does not support precedence declarations.  Therefore, we encode the
precedences and associativities of the operators into the grammar by introducing one syntactical variable per
precedence level, as discussed in Section \ref{section:operator-precedence}.
\begin{enumerate}
\item Line 2--12 define Boolean expressions:
      \begin{enumerate}[(a)]
      \item A \mytt{bool\_expr} is a list of \mytt{conjunction}s that are separated by the operator
            \quoted{||}, which represents \blue{logical or}.
      \item A \mytt{conjunction} is a list of \mytt{negation}s that are separated by the operator
            \quoted{\&\&}, which represents \blue{logical and}.  Hence, \quoted{\&\&} binds stronger than
            \quoted{||}.
      \item A \mytt{negation} is a \mytt{bool\_atom} that is preceded by an arbitrary number of negation
            operators \quoted{!}.
      \item A \mytt{bool\_atom} is either a comparison of two arithmetic expressions or a Boolean expression
            in parentheses.
      \end{enumerate}
      As the operators \quoted{||} and \quoted{\&\&} are left associative, the corresponding rules are
      \blue{left recursive}:  the syntactical variable on the left hand side of the rule occurs as the first
      symbol on the right hand side.  The operator \quoted{!} is right associative, since we want to interpret an
      expression of the form $\mytt{!!}a$ as  $\mytt{!}(\mytt{!}a)$.  Hence, the rule for \mytt{negation}
      is \blue{right recursive}.  The comparison operators \quoted{==}, \quoted{!=}, \quoted{<=},
      \quoted{>=}, \quoted{<}, and \quoted{>} are non-associative, since our programming language disallows
      the chaining of comparison operators.  Therefore, the rules for \mytt{bool\_atom} are not recursive at
      all and an expression of the form $x < y < z$ is syntactically invalid.
\item The operators are the heads of the tuples, for example the alternative \mytt{bool\_expr "||" conjunction}
      yields a tuple of the form $(\squoted{||}, \textsl{lhs}, \textsl{rhs})$.  An alternative that consists of a
      single symbol, like \mytt{bool\_expr: conjunction}, returns the tuple of this symbol.  Without this rule,
      the abstract syntax tree of the expression \mytt{x == 1} would contain a chain of four nested tuples.
      Line 11 uses an inner alternative, which abbreviates six alternatives, one for every comparison operator.
      Hence, the comparison operator that has been read is the head of the tuple.
\item Line 14--23 define arithmetic expressions in the same way:  The operators \quoted{+} and \quoted{-}
      have a lower precedence than the operators \quoted{*}, \quoted{/}, and \quoted{\%}.  As all of these
      operators are left associative, all rules are left recursive.  As the parentheses are ignored, the last
      alternative of the rule for \mytt{factor} consists of a single symbol, so a parenthesized expression does not
      create a tuple of its own.
\item Line 22 describes a function call.  Its arguments are written inline as a possibly empty list of
      expressions that are separated by commas.  The children of an optional part and of a repetition are spliced
      into the tuple of the alternative and the alias \quoted{call} replaces the head.  Hence, a function call is
      represented as a tuple of the form $(\squoted{call}, \textsl{name}, \textsl{arg}_1, \cdots,
      \textsl{arg}_n)$.
\end{enumerate}

Line 1 concatenates the grammar rules and the terminal definitions.  In line 3, the keyword argument
\mytt{start='program'} declares \mytt{program} to be the start variable of our grammar.  This argument could be
omitted, since the first rule of the grammar defines the start variable.  \simtextsc{Larkita} writes a description
of all states of the generated LR(1) parser into the file \mytt{compiler.out}, and it issues a
\mytt{ConflictWarning} because the parse table has a shift-reduce conflict.  The section \mytt{Conflicts} of the
file \mytt{compiler.out} shows that there is only one conflict:
\\[0.2cm]
\hspace*{1.3cm}
\mytt{State 246, shift/reduce conflict on "else", resolved as shift}
\\[0.2cm]
This is the conflict caused by the dangling else problem that has been discussed above.  All other conflicts have
been eliminated by stratifying the grammar.

    def simplify_leaves(ast):
        match ast:
            case ('NAME', name):
                return name
            case ('NUMBER', digits):
                return ('Number', digits)
            case (head, *children):
                return (head, *[simplify_leaves(child) for child in children])
\end{minted}

\end{figure}

The parser that is generated by \simtextsc{Larkita} returns the abstract syntax tree as a \blue{nested
tuple}\index{nested tuple}.  We have chosen the grammar in such a way that these tuples are exactly the nested
tuples that are processed by the code generator that is presented in the next section:
\begin{enumerate}[(a)]
\item A list of $n$ items is represented as the nested tuple $(\squoted{.}, \textsl{item}_1, \cdots,
      \textsl{item}_n)$.  For example, a program consisting of the functions $f_1$, $\cdots$, $f_n$ is
      represented as $(\squoted{.}, f_1, \cdots, f_n)$.
\item A function definition is represented as the nested tuple
      \\[0.2cm]
      \hspace*{1.3cm}
      $(\squoted{fct}, \textsl{name}, \textsl{parameters}, \textsl{variables}, \textsl{statements})$.
\item A variable is represented as a string, while a number is represented as a pair of the form
      $(\squoted{Number}, \textsl{digits})$.
\item All other nodes are represented as tuples whose first component is the operator.
      For example, the abstract syntax tree of an assignment is a tuple of the form
      $(\squoted{=}, \textsl{name}, \textsl{expr})$.
\end{enumerate}
There is only one exception:  \simtextsc{Larkita} represents a token as a pair consisting of the name of the token
and its text.  Hence, the parser represents a variable as a pair of the form $(\squoted{NAME},
\textsl{name})$ and a number as a pair of the form $(\squoted{NUMBER}, \textsl{digits})$.  The function
\mytt{simplify\_leaves} that is shown in Figure \ref{fig:Compiler.ipynb-4} on page
\pageref{fig:Compiler.ipynb-4} converts these pairs into the representation that is expected by the code
generator.  The pattern \mytt{(head, *children)} in line 7 matches all other tuples:  Their head is kept,
while their children are simplified recursively.
